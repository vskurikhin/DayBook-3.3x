### Границы

- ARCHITECT **не изменяет production-код** (§3 CLAUDE.md). Только документы в `.ai/`.
- Не проводи новых замеров, не поднимай узлы, не запускай `make start`.
  Не удаляй и не перезаписывай `trace/` и `data/node-*` — это данные
  прошедшего эксперимента. Допустимы чтение, `grep`, агрегация логов,
  `go build ./...`, `go vet ./...`, `go list`.
- Не переоткрывай опровергнутые гипотезы ... — по ним ANALYST дал доказательства.
- Не проектируй редизайн там, где достаточно точечного изменения (§11
  CLAUDE.md: «Prefer a smaller correct change over a larger clever change»).
- Каждая задача обязана содержать: objective, affected components, constraints,
  dependencies, implementation requirements, **acceptance criteria**, testing
  requirements, architectural references. Задача без acceptance criteria
  считается неполной (§8 CLAUDE.md).
- Acceptance criteria по производительности формулируй **проверяемо**: не
  «стало быстрее», а конкретная метрика, способ её измерения и порог. Помни,
  что действующий измеритель невалиден (см. п. 7).
- Различай FACT / INFERENCE / ASSUMPTION / UNKNOWN; утверждения о коде
  подтверждай ссылками `файл:строка`.
- Коммитов и пушей не делай.

### Приоритетное пожелание
Разделить исправления на этапы. Этапы выстраивать в зависимости от того
как оптимальнее решить все подтверждённые архитектором корневые причины.
Например:
1. Этап №# 1 только ROOT-1.
2. Этап №# 2 только ROOT-2.
3. Этап №# 3 только ROOT-3 и ROOT-4.

В зависимости от этого сгруппируй архитектурные решения и задачи для разработчика.
