дефект; вопрос классификации — §8 п. 6); (в) объём трейсов ~2 ГБ/сутки —

Приоритеты репозитория (AGENTS.md): корректность → простота →
сопровождаемость → производительность → удобство разработки. Плавающий
тест бьёт по двум краям сразу: он обесценивает шлюз корректности
(«красный — это шум или дефект?») и замедляет разработку (ложные стопы,
перезапуски). Веха двигает первое и пятое, не меняя продакшен-поведение
(кроме случая §3, «вне области», п. 2).

## 2. Целевое состояние

Рабочие пакеты (корневой `*.go` и `./pkg/...`) и ночной конвейер:

- **Реестр флаков.** Каждый плавающий тест имеет запись: имя, частота
  отказов (по ночным прогонам), гипотеза/причина, статус (триаж /
  исправляется / закрыт / осознанно принят), дата.
- **Политика шлюза.** Формализовано, когда ночной красный блокирует работу
  (или не блокирует), сколько повторов допустимо и для кого; сегодняшняя
  персональная льгота `TestSnapshot_LeaderCrash` («один повтор»)
  заменяется общей политикой.
- **Окно стабильности.** Непрерывная серия зелёных ночных прогонов
  фиксированной длины — критерий «стабильно» (число — вопрос владельца,
  §8 п. 3).
- **Запрет ложной стабилизации.** Устранение флака ослаблением или
  удалением утверждения теста не допускается; единственный законный исход
  — устранение причины (в тесте или, если флак её вскрывает, в
  продакшен-коде).

## 3. Границы вехи

**В области:**
- тесты рабочих пакетов и ночной стресс-конвейер;
- триаж и закрытие реестра известных флаков (таблица §1);
- нагрузочный стенд (§1.1): как источник наблюдений для триажа и среда
  воспроизведения редких событий (длительные прогоны); классификация
  стендовых наблюдений — тест-флак, наблюдаемая нестабильность кластера
  или дефект продакшена — выполняется на SG-0;
- методика: воспроизведение (серии `-count`, `-race`, ночные логи,
  длительные прогоны стенда), классификация причин (тайминги/порядок
  гонки/ресурсы/недетерминизм приспособления), правила доказательности;
- автоматизация триажа по журналам ночного CI (минимально необходимая);
- политика повторов; ночной шлюз остаётся информационным (ответ владельца
  на §8, п. 2) — блокирующим не делается.

**Вне области:**
- учебные каталоги `part1..part3`, `part4kv`, `part5kv`: плавающие тесты в
  них игнорировать — не триажировать, не исправлять (AGENTS.md);
- ускорение тестов и производительность (программа P-PERF-2), включая
  производительность на стенде: латентности/RPS/частота выборов сами по
  себе — материал P-PERF-2; стенд используется здесь только как источник
  редких событий и среда воспроизведения;
- исправление продакшен-дефектов как таковое: если триаж вскрывает дефект
  продакшена, минимальный фикс внутри вехи допустим (ответ владельца на
  §8, п. 4), крупнее — отдельной задачей/вехой; решение за ARCHITECT'ом;
- рефакторинг продакшен-кода вне причин флаков;
- новые зависимости и архитектурные изменения.

## 4. Цели (goals)

1. **S-1 (реестр).** Полный реестр плавающих тестов рабочих пакетов по
   ночным прогонам и архивам; каждая запись закрыта: причина установлена,
   тест стабилизирован — либо статус «осознанно принят» с обоснованием
   ARCHITECT'а (ADR). Наблюдения стенда (§1.1) проходят ту же процедуру
   классификации на SG-0 (граница с P-PERF-2 — §8 п. 6).
2. **S-2 (политика шлюза).** Ночной стресс-конвейер формально подключён
   или осознанно оставлен неблокирующим; политика повторов описана и
   применяется машиной, а не ad-hoc решением человека.
3. **S-3 (окно стабильности).** N зелёных ночных прогонов подряд
   (COUNT=10) на момент шлюза вехи.
4. **S-4 (класс приспособлений).** ПРЕДМЕТ 2 техдолга TODO-22 (недостижимые
   приспособления как класс) закрыт: проверка наличия класса выполнена,
   найденные экземпляры исправлены либо класс принят с обоснованием.
5. **S-5 (доказательность).** Ни одно «исправление» флака не ослабляет
   утверждения теста (ревью обязательное); для каждого закрытия —
   механизм воспроизведения и демонстрация, что до фикса отказ
   воспроизводился, после — нет.
6. **S-6 (гигиена).** Правила AGENTS.md соблюдены: терминология,
   приспособления достижимы, `gofmt`/`go vet`/lint без замечаний.

## 5. Критерии успеха / точки вехи

| Точка    | Содержание                                                                                                                | Критерий прохождения                                                                              |
|----------|---------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------|
| **SG-0** | Аналитик: инвентаризация плавающих тестов (ночные логи, архивы, серии) и наблюдений стенда (§1.1), методика триажа, риски | `handoff`; вердикт ANALYSIS_COMPLETE                                                              |
| **SG-1** | Архитектор: ADR (политика шлюза, порог окна стабильности, судьба реестра) + задачи TASK-SN-NNN                            | ADR + задачи с проверяемыми AC; ревью senior-architect                                            |
| **SG-2** | Реализация по задачам                                                                                                     | Каждая задача: IMPLEMENTATION_COMPLETE + серии `-race -count`                                     |
| **SG-3** | Шлюз вехи: окно стабильности                                                                                              | N зелёных ночных прогонов подряд; реестр закрыт; отчёт о закрытии вехи (по образцу stage-closure) |

Definition of Done вехи: SG-0…SG-3 пройдены; численность реестра
«до/после» зафиксирована; осознанно принятые флаки обоснованы ADR.

## 6. Риски и ограничения

| Риск                                                                                                            | Митигация                                                                                                              |
|-----------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------|
| Флак — симптом продакшен-дефекта; «стабилизация» теста замаскирует дефект                                       | Правило: сначала причина, потом фикс; вскрытый дефект продакшена — отдельная задача; ревью обязательное                |
| Ложная стабилизация (ослабление утверждений, увеличение таймаутов)                                              | Запрет в требованиях каждой задачи; дифф-ревью утверждений теста                                                       |
| Стоимость: ночные прогоны и серии `-count` занимают часы                                                        | Бюджет прогонов в задачах; триаж по журналам CI, а не слепые повторы                                                   |
| Недетерминизм не воспроизводится на машине разработчика                                                         | Воспроизведение сериями в CI-условиях и длительными прогонами стенда (§1.1); порог частоты для признания «неплавающим» |
| Смешение дисциплин: наблюдения стенда (потеря кворума, VERIFY bad) — не тест-флаки; риск подмены целей P-PERF-2 | Классификация на SG-0 (тест / наблюдаемая нестабильность / дефект); граница с P-PERF-2 — §8 п. 6; вынос по §8 п. 4     |
| Стоимость: трейсы стенда ~2 ГБ/сутки; хранение и разбор                                                         | Уровень трассировки длительных прогонов — заметка для SG-0; выгрузка отчётов в `data/reports/` по образцу текущего     |
| Пересечение с CLEAN-CODE-0 (декомпозиция меняет те же файлы)                                                    | Веха открывается строго после закрытия CLEAN-CODE-0 (ответ владельца на §8 п. 1)                                       |
