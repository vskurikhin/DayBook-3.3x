# :rowboat:  Raft

[English version](README-en.md)

Реализация алгоритма распределённого консенсуса Raft на языке Go и
построенный на ней реплицированный сервис «ключ–значение» с HTTP API.

## О проекте

Репозиторий содержит рабочий код консенсус-модуля Raft (выборы лидера,
репликация журнала, фиксация записей, снимки) и реплицированного
хранилища «ключ–значение» с HTTP API, Go-клиентом и генератором
нагрузки. Рабочий код — корневой пакет модуля `github.com/vskurikhin/raft`,
`pkg/...`, `cmd/...`, `internal/...`.

Проект сопровождается серией статей:

* [Часть 0: Введение](https://svn.su/2020/2020-02-22-implementing-raft-part-0-introduction.html)
* [Часть 1: Выборы](https://svn.su/2020/2020-02-24-implementing-raft-part-1-elections.html)
* [Часть 2: Команды и репликация логов](https://svn.su/2020/2020-02-29-implementing-raft-part-2-commands-and-log-replication.html)
* [Часть 3: Сохранение состояния и оптимизации](https://svn.su/2020/2020-05-05-implementing-raft-part-3-persistence-and-optimizations.html)
* [Часть 4. База данных «ключ–значение»](https://svn.su/2024/2024-10-10-implementing-raft-part-4-key-value-database.html)
* ~~Часть 5. Доставка сообщений «ровно один раз» (Exactly-Once Delivery)~~ _todo_

Каталоги `part1`–`part5kv` — учебные стадии построения проекта,
соответствующие частям серии статей (часть 0 вводная и кода не
содержит). Каждый учебный каталог самодостаточен и повторяет код
предыдущих частей: сравнение каталогов показывает эволюцию реализации.
Рабочий код развивается отдельно от учебных каталогов; длинные тестовые
прогоны по учебным каталогам не выполняются (см. раздел «Тестирование»).

## Возможности

* выборы лидера с предварительным голосованием (pre-vote), не повышающим
  терм при потере связи с кластером;
* репликация журнала и фиксация записей кворумом;
* снимки состояния машины состояний и восстановление узла из снимка;
* изменение состава кластера — добавление голосующего и неголосующего
  узла, понижение голосующего, удаление узла (один сервер за одно
  изменение);
* передача лидерства на указанный узел без перевыборов;
* future-объекты для асинхронных клиентских операций;
* транспорты TCP и внутрипроцессный; транспорт создаётся вызывающей
  стороной и передаётся узлу через конфигурацию;
* реплицированный KV-сервис с REST API поверх HTTP;
* Go-клиент KV-сервиса с поиском лидера и повторами запросов;
* генератор нагрузки `loadkv`.

## Архитектура

Слои сверху вниз:

```
┌─────────────────────────────────────────────────────────────────┐
│ KVService (pkg/kvservice)                                       │
│ HTTP API • DataStore • реализует raft.FSM                       │
└─────────────────────────────────────────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│ Server (server.go)                                              │
│ связывает переданный извне транспорт и ConsensusModule          │
└─────────────────────────────────────────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────────┐
│ ConsensusModule (raft_cm_*.go)                                  │
│ зависит только от интерфейсов Transport, Storage,               │
│ SnapshotStore, FSM                                              │
└─────────────────────────────────────────────────────────────────┘
```

* **KVService** принимает HTTP-запросы, ставит команды записи в очередь
  консенсус-модуля и применяет зафиксированные записи журнала к
  локальному хранилищу DataStore, реализуя интерфейс `raft.FSM`.
* **Server** — обёртка, создающая ConsensusModule поверх транспорта,
  переданного через `Config.Transport`; подключает и отключает соседей,
  останавливает узел.
* **ConsensusModule** реализует протокол Raft и зависит только от
  интерфейсов `Transport`, `Storage`, `SnapshotStore`, `FSM` — хранилище
  и транспорт передаются узлу извне через конфигурацию.

Автомат состояний консенсус-модуля:

```
Старт ────────────┐
                  ▼                    обнаружен
               ВЕДОМЫЙ ◄────────────────────┐более
               │     ▲      (becomeFollower)│высокий
               │     │                      │ term
       истекает│     │обнаруживает          │
         время,│     │нынешнего           ЛИДЕР
     начинаются│     │лидера                ▲
        выборы.│     │или новый терм        │
startElection()│     │                      │
               ▼     │                      │
         ПРЕДКАНДИДАТ│                      │
               │     │                      │
          успех│     │                      │
       pre-vote│     │                      │
               │     │                победа│
               КАНДИДАТ ────────────────────┘
               │     ▲               на выборах
               └─────┘
Любое состояние ──► Dead (через Stop())
```

Узел стартует ведомым. По истечении тайм-аута выборов он сначала
проводит предварительное голосование (pre-vote), не повышая терм, — это
предотвращает сбойные перевыборы узла, временно потерявшего связь. При
успехе pre-vote узел становится кандидатом и проводит выборы; получив
голоса кворума, становится лидером. Больший терм или обнаружение
действующего лидера возвращает узел в ведомые из любого активного
состояния. Остановка узла (`Stop`) переводит его в состояние DEAD.

## Быстрый старт

```sh
make build          # сборка bin/raftkv и bin/loadkv
make start-raft     # стенд: 3 узла + генератор нагрузки
make stop-raft      # остановка стенда
```

Цель `make start-raft` сначала останавливает предыдущий стенд, затем
запускает 3 узла raftkv: HTTP API слушает порты 8881–8883, RPC — порты
9991–9993. Через 2 секунды после старта узлов запускается генератор
нагрузки loadkv; по умолчанию он работает 5 минут
(`DURATION=5m`) и завершается сам.

Остановка и очистка: `make stop-raft` останавливает генератор и узлы;
`make stop` дополнительно удаляет pid-файлы; цели `make clean`,
`make clean-build-files`, `make clean-data-files`, `make clean-pid-files`,
`make clean-trace-files` удаляют артефакты сборки, данных и трейсов.

Переменные стенда переопределяются из командной строки make без правки
Makefile, например `make start-raft DURATION=1m`:

| Переменная             | Флаг узла или генератора | Умолчание Makefile |
|------------------------|--------------------------|--------------------|
| `APPLY_BATCH_INTERVAL` | `-apply-batch-interval`  | 50                 |
| `HEARTBEAT_TIMEOUT`    | `-heartbeat-timeout`     | 45                 |
| `REELECTION_TIMEOUT`   | `-reelection-timeout`    | 500                |
| `TICKER_TIMEOUT`       | `-ticker-timeout`        | 20                 |
| `TRACE_LOG_LEVEL`      | `-trace-log-level`       | 0                  |
| `CONCURRENCY`          | `-concurrency`           | 8                  |
| `DELETE_PERCENT`       | `-delete-percent`        | 0                  |
| `DURATION`             | `-duration`              | 5m                 |
| `GET_PERCENT`          | `-get-percent`           | 75                 |
| `REQUEST_RATE`         | `-request-rate`          | 200                |
| `VALUE_SIZE`           | `-value-size`            | 128                |
| `VERIFY_PERCENT`       | `-verify-percent`        | 33                 |
| `WEAK_GET_PERCENT`     | `-weak-get-percent`      | 0                  |
| `STAND`                | —                        | пусто              |

Переменная `STAND` задаёт префикс имён файлов артефактов стенда
(трейсы, stdout/stderr, pid-файлы) и позволяет различать наборы
артефактов. Префикс не меняет порты узлов и каталоги данных, поэтому
запускать два стенда одновременно в одном рабочем дереве нельзя.

## HTTP API

KV-сервис принимает JSON-запросы по шести маршрутам:

| Маршрут                  | Назначение                                          |
|--------------------------|-----------------------------------------------------|
| `GET /verifyleader/`     | проверка, что узел — действующий лидер              |
| `GET /weak-get/{key...}` | слабое чтение значения по ключу без записи в журнал |
| `POST /cas/`             | условная запись: сравнение и обмен значения         |
| `POST /delete/`          | удаление ключа                                      |
| `POST /get/`             | чтение значения по ключу через журнал               |
| `POST /put/`             | запись значения по ключу                            |

Бизнес-ответы всегда возвращаются с кодом HTTP 200, итог операции
передаётся полем `RespStatus`: `StatusOK` — операция выполнена;
`StatusNotLeader` — операция не подтверждена данным узлом (узел не
лидер, истёк тайм-аут постановки команды в очередь консенсус-модуля,
лидерство утрачено или передаётся, узел останавливается), клиенту
следует повторить команду на другом адресе. Полный справочник маршрутов,
форматов запросов и ответов, гарантий доставки и поведения Go-клиента —
[docs/API-HTTP.md](docs/API-HTTP.md).

## Конфигурация и флаги

Значения по умолчанию для временных параметров узла:

| Параметр                                                | Узел (умолчание флага) | Стенд (Makefile) |
|---------------------------------------------------------|------------------------|------------------|
| Период пульса (`-heartbeat-timeout`)                    | 33 мс                  | 45 мс            |
| Базовый тайм‑аут выборов (`-reelection-timeout`)        | 430 мс                 | 500 мс           |
| Шаг таймера выборов (`-ticker-timeout`)                 | 20 мс                  | 20 мс            |
| Интервал пакетного применения (`-apply-batch-interval`) | 50 мс                  | 50 мс            |
| Уровень трассировки (`-trace-log-level`)                | 1                      | 0                |

Между параметрами действует инвариант
`reelection-timeout ≥ 10·heartbeat-timeout` (а также
`ticker-timeout ≤ reelection-timeout/10`,
`apply-batch-interval ≤ reelection-timeout` и
`reelection-timeout > 2 × raft.TCPRPCTimeout = 400 мс`).
Проверка выполняется при старте по стратегии немедленного отказа:
недопустимая комбинация завершает процесс до начала работы, сообщение
перечисляет все нарушения.

Полный справочник флагов raftkv и loadkv с умолчаниями и границами
значений — [docs/Flags.md](docs/Flags.md); транспортный тайм-аут RPC и
остальные флаги описаны только там.

## Тестирование

```sh
go test . ./pkg/...      # рабочие пакеты: корневой пакет и pkg/...
go test -race . ./pkg/...
make test-stress COUNT=3 # последовательные прогоны под -race
```

Тесты корневого пакета используют реальные таймеры и выполняются
медленно — это ожидаемо, тайм-аут прогона задан с запасом. Каталоги

## Наблюдаемость

Стенд пишет трейсы консенсус-модуля и KV-сервиса в файлы
`trace/raftcm-N.trace` и `trace/raftkv-N.trace`, а стандартные выводы
узлов — в `trace/raftkv-N.stdout` и `trace/raftkv-N.stderr`. Флаги
профилирования: `-pprof-addr` (адрес отдельного HTTP-сервера
профилирования; пустое значение выключает), `-block-profile-rate`,
`-mutex-profile-fraction`.

Флаг `-trace-log-level` задаёт порог трассировки консенсус-модуля.
Сообщение уровня l печатается при l < порога; константы слоёв сообщений
— 0/1/2/4/8/16. Действует флаг так:

* при `-trace-log-level=0` вывод
  секундной статистики консенсус-модуля в stdout полностью отключён:
  не печатается ни строка латентности, ни строка счётчиков;
* при значении ≥ 1 раз в секунду печатаются обе строки — отчёт
  латентности и отчёт счётчиков;
* дальнейшие ступени порога добавляют слои трассировочных сообщений,
  не отключая предыдущие: 1 — ключевые события (смена роли и терма,
  голосования), 2 — течение циклов выборов и лидера, 3 — результативные
  события (победа на выборах, продвижение индекса фиксации), 5 —
  предварительное голосование и отправка снимков, 9 — репликация
  (AppendEntries, пульс), 17 — полный дамп журнала;
* значение флага по умолчанию (в скомпилированной программе) — 1.
  Для стенда в Makefile задано TRACE_LOG_LEVEL=0, поэтому вывод
  секундной статистики в stdout отключён.

Файлы трейсов задаются флагами `-trace-cm-log-file` и
`-trace-kv-log-file` (пустое значение — стандартный вывод ошибок).

### Сводка генератора нагрузки loadkv

По завершении прогона генератор печатает сводку; начиная с версии 1.2.0
в неё добавлены строки `rps:` и `ops:` после строк времени ответа.
Сообщения сводки выводятся через `slog` с меткой времени и уровнем
`INFO`; на стенде они записываются в `trace/loadkv.out`. Ниже приведён
пример формата: значения условные и взяты не из одного прогона.

    rps: seconds=3 mean=200.0 median=200.0 stddev=10.0 min=190 max=210 total=600
    ops: done=29903 (get=75.2% put=24.8% verify=0.0% weak-get=0.0% delete=0.0% delete-verify=0.0%)

Строка `rps:` содержит статистику посекундной скорости операций.
Раз в секунду генератор печатает строку `RPS=` и сохраняет её значение
в ряд, по которому затем рассчитывает сводку:

* `seconds` — число учтённых секунд после исключения первой;
* `mean` — среднее арифметическое посекундных значений, операций
  в секунду, с одним знаком после запятой;
* `median` — центральное значение упорядоченного ряда; при чётном
  числе значений — полусумма двух центральных;
* `stddev` — выборочное стандартное отклонение, операций в секунду,
  с делителем n−1, где n — число учтённых секунд; при одной секунде
  равно нулю;
* `min` и `max` — минимальное и максимальное значения ряда;
* `total` — сумма учтённых значений.

Первая секунда исключается из всех величин как стартовое окно
установления соединений. Если за прогон напечатано меньше двух строк
`RPS=`, все величины в строке `rps:` равны нулю, включая `seconds=0`.

RPS за секунду — приращение общего числа завершённых операций шести
видов: `get`, `put`, `verify`, `weak-get`, `delete`, `delete-verify`.
Учитываются и успешные операции, и операции, завершившиеся ошибкой.
Перечитывания после записи или удаления учитываются отдельно
(`verify`, `delete-verify`), поэтому скорость операций может превышать
темп, заданный флагом `-request-rate`. Ошибки вызовов отражаются в
полях `fail` строк `done:` и `RPS=`. Поля `bad` проверок перечитывания
учитывают ошибки и расхождения значений; расхождения требуют разбора
и сами по себе не означают отказа сервиса. Счётчики `DELETE-VERIFY
ok/bad` есть только в строке `done:`.

В ряд входят только секунды с напечатанной строкой `RPS=`. Интервал
от последней такой строки до остановки прогона в статистику не входит.
Операции, начатые до остановки и завершившиеся после неё, учитываются
в `done:` и `ops:`, но не в `rps:`. Поэтому `rps: total` не превышает
`ops: done`.

Строка `ops:` показывает полное число завершённых операций за прогон
(`done`) и долю каждого вида в процентах. При `done=0` все доли равны
`0.0`. Начиная с версии 1.2.0 последняя строка сводки — `ops:`;
ранее ею была строка времени ответа `DELETE`. Разбор по префиксу
сообщения сохраняется, а разбор по позиции от конца вывода меняется.

Начиная с версии 1.2.0 генератор выпускает запросы по абсолютному
расписанию. Если пробуждение тикера опаздывает, генератор обрабатывает
все тики, чей срок уже наступил: опоздание не приводит к их потере.
Если ограничитель одновременности занят, запрос не выпускается,
а тик учитывается счётчиком `_dropped`. Таким образом, начиная с версии 1.2.0
счётчик учитывает каждый наступивший по расписанию, но невыпущенный
тик, включая тики, обработанные после опоздавшего пробуждения.
До версии 1.2.0 учитывались лишь тики, застигнутые на занятом
ограничителе в момент пробуждения. Значения `_dropped` несравнимы
с прогонами прежних версий. При том же `-request-rate` числа сводки
также могут отличаться от прогонов версий до 1.2.0 и не подходят
для прямого сравнения с ними.

Формат строк `run:` и `done:` прежний. Набор флагов генератора и их
умолчания не изменены. Изменение касается только генератора:
узлы `raftkv` и протоколы не затронуты.
